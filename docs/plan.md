# CropMix Twin — план на 9 дней (12–20 ноября 2026), версия 2

## Контекст
Конкурс Xylem (трек Water Quantity), подача до 20.11.2026.
Строим модель планирования для Кызылординской области: структура посевов → водопотребление и доход →
структура, которая экономит воду при заданных ограничениях. Основа — ETc = ET0 × Kc (FAO-56),
поверх неё по порядку: слой 1 (потери), слой 2 (водность), слой 3 (LP), бэктест, чувствительность.

**Ключевые решения версии 2:**
1. Тонкая рабочая версия целиком (движок + слой 1 + веб с ползунками на assumed-данных) готова к концу дня 4.
2. Кнопка «Оптимизировать» работает вживую по заранее посчитанной сетке (обоснование — в модуле 7).
3. Строгие правила для `status=real`: ссылка, страница/таблица, точная цитата в SOURCES.md.
4. На дни 8–9 запланированы видео-демо и текст заявки.

**Режим работы:** каждую правку файлов подтверждает автор вручную. Один модуль за раз, после каждого — git commit.

## Общие решения
- **Формат данных:** «длинные» CSV, одна строка — одно число:
  `entity, param, year, value, unit, source, status` (status ∈ real/assumed/simulated).
  В колонке `source` — id записи в SOURCES.md (например, `S012`) или короткое обоснование допущения.
- **Правило для real:** у каждого числа со `status=real` в `data/SOURCES.md` есть запись:
  id · ссылка · документ · страница/таблица/строка · **точная цитата** (как в источнике, с единицами) · дата обращения.
  Если источник не открывается или не читается (PDF-скан, платный доступ, сайт недоступен) или есть сомнения
  в числе (единицы, год, область против республики), ставим `assumed` и явно сообщаем об этом.
  Тест проверяет, что у каждого real-числа есть id и запись в SOURCES.md с непустой цитатой.
- **Единицы:** га, м³, мм. Пересчёт только в `src/units.py` (1 мм·га = 10 м³), на него есть тест.
- **Культуры (старт):** рис, пшеница, люцерна, кукуруза (зерно/силос), бахчевые, овощи, картофель —
  окончательный список берём из статистики.
- **Сезон:** апрель–октябрь, расчёт по дням, итог за сезон.
- **Тесты:** pytest, ≥3 ручных примера на модуль.

## Модули

### 0. Настройка (день 1)
- `requirements.txt` (pandas, numpy, scipy, pytest), `.gitignore`, `README.md`-заготовка, `git init`, первый commit.

### 1. Данные
- Файлы: `data/climate_daily.csv`, `data/crops_fao56.csv`, `data/crop_areas.csv`, `data/yields.csv`,
  `data/prices.csv`, `data/costs.csv`, `data/efficiency.csv`, `data/water_withdrawal.csv`, `data/river_flow.csv`,
  `data/SOURCES.md`; код `src/data_loader.py`, `src/units.py`, `src/data_report.py`.
- Вход: скачанные таблицы и PDF. Выход: проверенные DataFrame'ы и отчёт «real/assumed» со списком всех assumed.
- Проверка: тест падает, если нет source или status; если status не из списка; если единица неизвестна;
  если значение вне правдоподобного диапазона; **если у real-числа нет записи с цитатой в SOURCES.md**.
- На дни 1–3 заполняем «стартовый» набор: климат NASA POWER (real, с цитатой из описания набора), Kc из FAO-56
  (real, таблица 12), площади, цены и затраты — сначала assumed, потом заменяем на найденные.

### 2. Движок ET0 × Kc
- Файлы: `src/et0.py` (Penman–Monteith FAO-56, ур. 6; запасной вариант — Hargreaves), `src/kc.py`
  (кривая Kc по 4 стадиям и климатическая поправка, ур. 62), `src/etc.py`.
- Вход: суточный климат и параметры культур. Выход: `crop × year → ETc` в мм и м³/га.
- Проверка: (1) пример 18 из FAO-56: ET0 = 3.9 мм/день ±0.1; (2) ручная интерполяция Kc;
  (3) ET0 = 5 мм, Kc = 1, 100 дней → 500 мм = 5000 м³/га; (4) порядок величины — см. решение 4 ниже (вместо CLIMWAT).
- **Решения автора по модулю 2 (подтверждены 2026-11-12):**
  1. ET0: Penman–Monteith по NASA POWER — основной расчёт; Hargreaves по станции GSOD — независимая сверка.
     NASA не содержит RHmin/RHmax, поэтому ea считается по ур. 19 (RHmean).
  2. RHmin для климатической поправки Kc (ур. 62): RHmin = ea / e°(Tmax) × 100.
  3. Люцерна (кормовые): сезон — от последнего весеннего до первого осеннего заморозка −4 °C (Tmin, NASA POWER);
     Kc = 0.95 после стадии развития, последние 30 дней — линейное снижение до 0.90; l_late = 30 дней — `assumed`.
  4. Вместо CLIMWAT: Hargreaves (GSOD) и литературное ET риса 10–11 тыс. м³/га (S083) — только проверка
     правдоподобия, **без калибровки** модели по ним.
  5. Климатическая поправка Kc_mid и Kc_end (ур. 62/65) применяется **ко всем культурам единообразно,
     включая люцерну** (кормовые): табличные 0.95/0.90 — исходные значения до поправки.

### 3. Слой 1 — эффективные осадки, КПД, потери
- Файл: `src/layer1_losses.py`. Pe (USDA SCS) → NIR = max(ETc − Pe, 0) → «на поле» = NIR / КПД_поля →
  «из реки» = / КПД_каналов.
- **Рис (решение автора 2026-11-12):** «на поле» = ETc + SAT + WL + PERC × дни затопления − Pe (FAO TM3, 4.4);
  SAT и WL однократно за сезон; КПД_поля к рису **не** применяется (потери уже в PERC); «из реки» = / КПД_каналов.
  Данные: `data/rice_water.csv` (все assumed).
- Выход: три величины на культуру: «у растения», «на поле», «из реки» (м³/га).
- Проверка: Pe = 0 при нулевых осадках; NIR ≥ 0; ручной пример: 600 мм, КПД 0.75 и 0.6 → 13 333 м³/га.

### 4. Тонкий веб (к концу дня 4)
- Файлы: `src/export_web.py` → `web/data/model.json`; `web/index.html`, `web/app.js`, `web/style.css`; Chart.js с CDN.
- Что умеет: ползунки площадей культур → вода (у растения / на поле / из реки) и доход пересчитываются в браузере
  (модель линейна по площади, поэтому JS-расчёт точный); столбчатый график; плашка «данные assumed» и ограничения модели.
- Проверка: (1) тест: JSON содержит все культуры, коэффициенты = Python; (2) три ручных набора площадей:
  браузер = Python; (3) открывается через file:// и на телефоне.
- **Итог дня 4:** рабочая версия «данные → движок → слой 1 → веб» целиком. Commit с пометкой v0.1.

### 5. Слой 2 — сценарии водности
- Файл: `src/layer2_scenarios.py`. Классы лет по стоку Сырдарьи или лимитам МКВК (выше 75-го перцентиля,
  25–75, ниже 25-го) → лимит воды и климатический год для каждого класса.
- Проверка: классификация ручного ряда; лимит маловодного ≤ среднего ≤ многоводного; без данных — сценарии с флагом assumed.

### 6. Слой 3 — оптимизатор (scipy linprog)
- Файл: `src/layer3_optimizer.py`. Переменные — площади (га). Цель: минимум воды из реки или максимум дохода.
  Ограничения: вода ≤ лимит; Σплощадь ≤ орошаемая; продовольственные ≥ минимум; доход ≥ минимум;
  границы ±X% от текущей площади по каждой культуре.
- Выход: структура, вода, доход, активные ограничения, понятное сообщение при невыполнимости.
- Проверка: задача на 2 культуры с ручным решением; невыполнимый случай; снятый лимит воды → ручной максимум; единицы.

### 7. Сетка для «Оптимизировать»
**Выбрана заранее посчитанная сетка, а не LP-решатель на JS.**
- Почему проще и надёжнее: истину считает один решатель (scipy), который уже покрыт тестами. Второй решатель
  на JS пришлось бы отдельно проверять на совпадение с scipy, а расхождение решателей на защите объяснить трудно.
  Задача маленькая, поэтому сетка считается за секунды.
- Как: `src/optimize_grid.py` → `web/data/grid.json`. Оси: сценарий водности (3) × лимит воды (~15 шагов) ×
  минимальный доход (~10 шагов) × цель (2) = ~900 LP-решений; JSON — порядка сотен КБ.
  В браузере ползунки «лимит воды» и «мин. доход» перескакивают по шагам сетки, кнопка мгновенно показывает
  оптимальную структуру, экономию относительно текущей и активные ограничения. Невыполнимые ячейки показываем
  как «при таких условиях решения нет».
- Ограничение: минимум продовольственных культур и коридор ±X% в вебе фиксированы (2–3 предустановки).
  Если позже понадобится менять всё свободно — можно добавить jsLPSolver, сверяя его с сеткой как с эталоном.
- Проверка: (1) случайные 20 ячеек пересчитываются scipy и совпадают с JSON; (2) при ослаблении лимита воды
  доход не падает (монотонность); (3) ячейка без ограничений = текущая или граничная структура, как вручную.

### 8. Бэктест
- Файл: `src/backtest.py`. Годы с реальными площадями и официальным водозабором → модель против факта:
  смещение %, MAE, корреляция. КПД на тех же годах не подгоняем (или подгоняем через leave-one-out и пишем об этом).
- Проверка: метрики на ручных рядах; идеальная модель → 0; пропущенный год пропускается, а не превращается в ноль.

### 9. Чувствительность
- Файл: `src/sensitivity.py`. По одному параметру ±10/20% (Kc, цены, урожайность, КПД) → вода, доход,
  экономия оптимального плана; tornado-график; итог — диапазон экономии «от–до».
- Проверка: 0% изменения = база; +10% Kc → +10% ETc; цены не влияют на воду при цели «минимум воды».

### 10. Документация, видео, заявка
- `docs/methodology.md`, `docs/limitations.md`, `docs/assumptions.md` (из data_report), `docs/presentation_notes.md`,
  `docs/demo_script.md` (сценарий видео по секундам), `docs/application.md` (черновик текста заявки), `README.md`.
- Проверка: каждое число в заявке и видео есть в outputs/ и указано с диапазоном и допущениями; ссылки SOURCES.md открываются.

## Чего, скорее всего, нет в открытом доступе (готовимся пометить assumed)
1. Затраты на гектар по культурам — максимум технологические карты или оценки из статей.
2. Подача воды по культурам и полям — есть только суммарный водозабор области.
3. Измеренный КПД конкретных каналов — только оценки (обычно 0.5–0.65) с диапазоном.
4. Суточные данные станций Казгидромета — платные; заменяем на NASA POWER + GSOD.
5. Местные Kc и перколяция на рисовых чеках — FAO-56 и литература.
6. Водозабор только на орошение без промывки засолённых земель и других нужд — частично; промывка — ограничение модели.
7. Официальные минимумы площадей продовольственных культур — политический параметр (assumed).
8. Лимиты МКВК за все годы — на CAWater-Info есть пробелы.
